<p>Aamu uses ShareDB and Operational Transformation (OT) for collaborative editing, with the server validating and ordering accepted changes.</p><p>CRDTs let replicas merge concurrent changes and are useful for local-first and offline collaboration. They can also be deployed with a central server.</p><p>Clients edit optimistically. ShareDB transforms concurrent operations, and the server stores and broadcasts the accepted state.</p><p>Documents live next to tasks, email, helpdesk, meetings, databases, forms, files, comments, permissions, automations, search, AI features, and team-level workflows. In that kind of product, the hardest problem is not only merging text edits. The harder problem is keeping the whole workspace consistent.</p><h2>The core tradeoff</h2><p>They are designed for situations where different users, devices, or replicas may edit the same data independently and later synchronize their changes. In an ideal CRDT-based system, users can keep working even without a stable connection, and the system can merge concurrent changes automatically.</p><p>But Aamu.app optimizes for a different set of constraints:</p><ul><li><p>clear permissions</p></li><li><p>predictable business logic</p></li><li><p>auditability</p></li><li><p>integration with other workspace objects</p></li><li><p>reliable automations</p></li><li><p>consistent search and AI indexing</p></li><li><p>a single source of truth for team data</p></li></ul><p>We chose a central authority to keep these checks and workflows in the existing backend. This deployment choice is separate from whether edits use OT or CRDTs.</p><p>A comment might become a task.<br>A document might be linked to a customer conversation.<br>A database row might reference a file or a helpdesk ticket.<br>An AI command might turn text into an action.<br>A permission change might immediately affect who is allowed to see or edit something.<br>A search index or Team Brain feature may need to update when content changes.<br>An automation may need to run exactly once when a specific event happens.</p><p>A server-authoritative model gives us a clear place to answer important questions:</p><ul><li><p>Is this user still allowed to make this change?</p></li><li><p>What is the canonical order of changes?</p></li><li><p>Which version of the document did this change apply to?</p></li><li><p>What other objects should be updated because of this change?</p></li><li><p>Should an automation run?</p></li><li><p>Should search or AI indexes be refreshed?</p></li><li><p>What should be written to the audit log?</p></li><li><p>What should other users see next?</p></li></ul><p>With ShareDB and OT, the server can decide these things in one controlled flow.</p><h2>Permissions are simpler with a central authority</h2><p>Permissions are one of the strongest reasons to prefer a central server in a business workspace.</p><p>Imagine a user opens a document, goes offline, and keeps editing for an hour. During that time, an admin removes their access to the workspace, the project, or the document.</p><p>What should happen when the user comes back online?</p><p>In a CRDT-first architecture, the system may have technically valid changes that can merge cleanly with the document. But from the business point of view, those changes may no longer be allowed.</p><p>CRDT-based applications can validate writes on a central server too. The permission boundary comes from the application’s authorization design, not from the merge algorithm.</p><p>In a server-authoritative model, the rule is more direct: the server validates every accepted change. If the user no longer has permission, the change is rejected.</p><h2>Business events need reliable processing</h2><p>But in Aamu.app, a document edit can also be part of a larger workflow. It might trigger an automation, update an activity feed, create a notification, refresh an AI context, or connect to another object in the workspace.</p><p>Ordering edits does not by itself guarantee exactly-once side effects.</p><p>Background jobs still need durable state, retry handling and deduplication. A central server gives us one place to coordinate that work.</p><p>When the server accepts an operation, it can also decide what else should happen. It can update related records, queue background jobs, send notifications, and record activity in a predictable order.</p><h2>Auditability matters in team software</h2><p>Aamu.app is built for teams and businesses. In that context, it is useful to know what happened and when.</p><p>A server-authoritative OT model gives us a simple history:</p><ul><li><p>operation accepted</p></li><li><p>document version updated</p></li><li><p>user recorded</p></li><li><p>timestamp stored</p></li><li><p>related events triggered</p></li><li><p>other clients notified</p></li></ul><p>CRDT systems can also record authorship and operation history. ShareDB’s ordered document versions fit Aamu’s existing storage and debugging tools.</p><h2>Offline-first is not our main product promise</h2><p>Search, permissions, automations, notifications, AI features, integrations, and cross-object workflows all depend on having a reliable shared backend.</p><p>We may still support local drafts, temporary offline resilience, and optimistic editing where it makes sense. But full local-first collaboration is not the central design goal.</p><h2>OT is a good fit for our needs</h2><p>Operational Transformation has a long history in collaborative editing. The basic idea is that users can make concurrent edits, and the system transforms operations so they can be applied in a consistent order.</p><p>ShareDB gives Aamu.app a practical foundation for this model.</p><p>With ShareDB, we get:</p><ul><li><p>real-time synchronization</p></li><li><p>optimistic local editing</p></li><li><p>server-side ordering of operations</p></li><li><p>a canonical document state</p></li><li><p>integration with our existing backend</p></li><li><p>a clear place for validation and authorization</p></li><li><p>a model that fits well with other server-side business logic</p></li></ul><h2>Why not use both?</h2><p>A product can use CRDTs for some local-first data, OT for document editing, server-side events for business workflows, and traditional database transactions for core records.</p><p>Aamu.app already combines many parts of work into one product. Adding a CRDT layer would not only mean changing the editor sync model. It would affect storage, migrations, permissions, version history, indexing, automations, testing, backups, and support.</p><p>For Aamu’s current requirements, ShareDB fits the backend we already operate.</p><h2>The tradeoff we accept</h2><p>Collaboration depends on the backend being available and responsive.
