<p xmlns="http://www.w3.org/1999/xhtml">Collaborative editing is one of those technical choices that looks simple from the outside and becomes very nuanced once you build a real product around it.</p><p xmlns="http://www.w3.org/1999/xhtml">A common question is: why not use CRDTs?</p><p xmlns="http://www.w3.org/1999/xhtml">CRDTs are a powerful approach to collaboration. They are especially attractive for local-first software, offline editing, peer-to-peer synchronization, and systems where multiple replicas need to merge changes automatically without a single central authority deciding the final order of operations.</p><p xmlns="http://www.w3.org/1999/xhtml">Aamu.app takes a different approach.</p><p xmlns="http://www.w3.org/1999/xhtml">Aamu.app uses ShareDB, which is based on Operational Transformation, often shortened to OT. In our architecture, collaboration is server-authoritative: clients can edit optimistically, but the server is the source of truth. The server validates, orders, applies, stores, and broadcasts changes.</p><p xmlns="http://www.w3.org/1999/xhtml">This is not because CRDTs are bad. They are not. It is because Aamu.app is not just a document editor.</p><p xmlns="http://www.w3.org/1999/xhtml">Aamu.app is a full workspace.</p><p xmlns="http://www.w3.org/1999/xhtml">Documents live next to tasks, email, helpdesk, meetings, databases, forms, files, comments, permissions, automations, search, AI features, and team-level workflows. In that kind of product, the hardest problem is not only merging text edits. The harder problem is keeping the whole workspace consistent.</p><h2 xmlns="http://www.w3.org/1999/xhtml">The core tradeoff</h2><p xmlns="http://www.w3.org/1999/xhtml">CRDTs are excellent when the primary goal is distributed editing.</p><p xmlns="http://www.w3.org/1999/xhtml">They are designed for situations where different users, devices, or replicas may edit the same data independently and later synchronize their changes. In an ideal CRDT-based system, users can keep working even without a stable connection, and the system can merge concurrent changes automatically.</p><p xmlns="http://www.w3.org/1999/xhtml">That is a very attractive model.</p><p xmlns="http://www.w3.org/1999/xhtml">But Aamu.app optimizes for a different set of constraints:</p><ul xmlns="http://www.w3.org/1999/xhtml"><li><p>clear permissions</p></li><li><p>predictable business logic</p></li><li><p>auditability</p></li><li><p>integration with other workspace objects</p></li><li><p>reliable automations</p></li><li><p>consistent search and AI indexing</p></li><li><p>a single source of truth for team data</p></li></ul><p xmlns="http://www.w3.org/1999/xhtml">For those constraints, a central server is often the simpler and safer architecture.</p><h2 xmlns="http://www.w3.org/1999/xhtml">Aamu.app is more than collaborative text</h2><p xmlns="http://www.w3.org/1999/xhtml">In a standalone document editor, the main question may be: how do we merge document edits?</p><p xmlns="http://www.w3.org/1999/xhtml">In Aamu.app, the question is broader: how do we keep the entire workspace correct when a document edit may affect other parts of the system?</p><p xmlns="http://www.w3.org/1999/xhtml">A comment might become a task.<br>A document might be linked to a customer conversation.<br>A database row might reference a file or a helpdesk ticket.<br>An AI command might turn text into an action.<br>A permission change might immediately affect who is allowed to see or edit something.<br>A search index or Team Brain feature may need to update when content changes.<br>An automation may need to run exactly once when a specific event happens.</p><p xmlns="http://www.w3.org/1999/xhtml">In this environment, collaboration is not only a sync problem. It is also a domain logic problem.</p><p xmlns="http://www.w3.org/1999/xhtml">A server-authoritative model gives us a clear place to answer important questions:</p><ul xmlns="http://www.w3.org/1999/xhtml"><li><p>Is this user still allowed to make this change?</p></li><li><p>What is the canonical order of changes?</p></li><li><p>Which version of the document did this change apply to?</p></li><li><p>What other objects should be updated because of this change?</p></li><li><p>Should an automation run?</p></li><li><p>Should search or AI indexes be refreshed?</p></li><li><p>What should be written to the audit log?</p></li><li><p>What should other users see next?</p></li></ul><p xmlns="http://www.w3.org/1999/xhtml">With ShareDB and OT, the server can decide these things in one controlled flow.</p><h2 xmlns="http://www.w3.org/1999/xhtml">Permissions are simpler with a central authority</h2><p xmlns="http://www.w3.org/1999/xhtml">Permissions are one of the strongest reasons to prefer a central server in a business workspace.</p><p xmlns="http://www.w3.org/1999/xhtml">Imagine a user opens a document, goes offline, and keeps editing for an hour. During that time, an admin removes their access to the workspace, the project, or the document.</p><p xmlns="http://www.w3.org/1999/xhtml">What should happen when the user comes back online?</p><p xmlns="http://www.w3.org/1999/xhtml">In a CRDT-first architecture, the system may have technically valid changes that can merge cleanly with the document. But from the business point of view, those changes may no longer be allowed.</p><p xmlns="http://www.w3.org/1999/xhtml">That does not mean CRDT systems cannot handle permissions. They can. But permission handling becomes a separate and often difficult layer on top of the sync model.</p><p xmlns="http://www.w3.org/1999/xhtml">In a server-authoritative model, the rule is more direct: the server validates every accepted change. If the user no longer has permission, the change is rejected.</p><p xmlns="http://www.w3.org/1999/xhtml">For Aamu.app, that simplicity matters.</p><p xmlns="http://www.w3.org/1999/xhtml">Teams need collaboration, but they also need access control they can trust.</p><h2 xmlns="http://www.w3.org/1999/xhtml">Business events should happen exactly once</h2><p xmlns="http://www.w3.org/1999/xhtml">A document edit is sometimes just a document edit.</p><p xmlns="http://www.w3.org/1999/xhtml">But in Aamu.app, a document edit can also be part of a larger workflow. It might trigger an automation, update an activity feed, create a notification, refresh an AI context, or connect to another object in the workspace.</p><p xmlns="http://www.w3.org/1999/xhtml">These side effects should not happen “eventually, maybe, after merge resolution, depending on which replica sees what first.”</p><p xmlns="http://www.w3.org/1999/xhtml">They should happen exactly once, based on an accepted server-side event.</p><p xmlns="http://www.w3.org/1999/xhtml">This is another reason why a central server works well for Aamu.app.</p><p xmlns="http://www.w3.org/1999/xhtml">When the server accepts an operation, it can also decide what else should happen. It can update related records, queue background jobs, send notifications, and record activity in a predictable order.</p><p xmlns="http://www.w3.org/1999/xhtml">That makes the product easier to reason about, easier to debug, and easier to operate.</p><h2 xmlns="http://www.w3.org/1999/xhtml">Auditability matters in team software</h2><p xmlns="http://www.w3.org/1999/xhtml">Aamu.app is built for teams and businesses. In that context, it is useful to know what happened and when.</p><p xmlns="http://www.w3.org/1999/xhtml">A server-authoritative OT model gives us a simple history:</p><ul xmlns="http://www.w3.org/1999/xhtml"><li><p>operation accepted</p></li><li><p>document version updated</p></li><li><p>user recorded</p></li><li><p>timestamp stored</p></li><li><p>related events triggered</p></li><li><p>other clients notified</p></li></ul><p xmlns="http://www.w3.org/1999/xhtml">This linear accepted history is valuable.</p><p xmlns="http://www.w3.org/1999/xhtml">It helps with debugging. It helps with restoring data. It helps with understanding user actions. It helps with support. It also makes it easier to build features such as activity feeds, version history, notifications, and audit logs.</p><p xmlns="http://www.w3.org/1999/xhtml">CRDT systems can also keep history, but the mental model is different. The system may contain distributed operations from multiple replicas that converge into the final state. That is powerful, but it can be harder to explain and operate in a business workspace where customers expect a clear source of truth.</p><h2 xmlns="http://www.w3.org/1999/xhtml">Offline-first is not our main product promise</h2><p xmlns="http://www.w3.org/1999/xhtml">One of the biggest advantages of CRDTs is offline-first editing.</p><p xmlns="http://www.w3.org/1999/xhtml">If the main promise of Aamu.app were “edit everything fully offline and sync later,” then CRDTs would be a very natural choice.</p><p xmlns="http://www.w3.org/1999/xhtml">But that is not the main promise of Aamu.app.</p><p xmlns="http://www.w3.org/1999/xhtml">Aamu.app is designed to reduce the fragmentation of work. The goal is to bring common team workflows into one consistent workspace: tasks, docs, email, helpdesk, meetings, databases, files, forms, and AI-assisted actions.</p><p xmlns="http://www.w3.org/1999/xhtml">That kind of product benefits from being connected to the server, because the server is where the team context lives.</p><p xmlns="http://www.w3.org/1999/xhtml">Search, permissions, automations, notifications, AI features, integrations, and cross-object workflows all depend on having a reliable shared backend.</p><p xmlns="http://www.w3.org/1999/xhtml">We may still support local drafts, temporary offline resilience, and optimistic editing where it makes sense. But full local-first collaboration is not the central design goal.</p><h2 xmlns="http://www.w3.org/1999/xhtml">OT is a good fit for our needs</h2><p xmlns="http://www.w3.org/1999/xhtml">Operational Transformation has a long history in collaborative editing. The basic idea is that users can make concurrent edits, and the system transforms operations so they can be applied in a consistent order.</p><p xmlns="http://www.w3.org/1999/xhtml">ShareDB gives Aamu.app a practical foundation for this model.</p><p xmlns="http://www.w3.org/1999/xhtml">With ShareDB, we get:</p><ul xmlns="http://www.w3.org/1999/xhtml"><li><p>real-time synchronization</p></li><li><p>optimistic local editing</p></li><li><p>server-side ordering of operations</p></li><li><p>a canonical document state</p></li><li><p>integration with our existing backend</p></li><li><p>a clear place for validation and authorization</p></li><li><p>a model that fits well with other server-side business logic</p></li></ul><p xmlns="http://www.w3.org/1999/xhtml">For Aamu.app, this is a good tradeoff.</p><p xmlns="http://www.w3.org/1999/xhtml">It keeps collaboration fast enough for users while keeping the backend understandable and authoritative.</p><h2 xmlns="http://www.w3.org/1999/xhtml">Why not use both?</h2><p xmlns="http://www.w3.org/1999/xhtml">It is possible to combine ideas from both worlds.</p><p xmlns="http://www.w3.org/1999/xhtml">A product can use CRDTs for some local-first data, OT for document editing, server-side events for business workflows, and traditional database transactions for core records.</p><p xmlns="http://www.w3.org/1999/xhtml">But every additional data model has a cost.</p><p xmlns="http://www.w3.org/1999/xhtml">Aamu.app already combines many parts of work into one product. Adding a CRDT layer would not only mean changing the editor sync model. It would affect storage, migrations, permissions, version history, indexing, automations, testing, backups, and support.</p><p xmlns="http://www.w3.org/1999/xhtml">That complexity has to pay for itself.</p><p xmlns="http://www.w3.org/1999/xhtml">For now, the benefits of CRDTs do not outweigh the operational simplicity and product consistency we get from ShareDB and a central server.</p><h2 xmlns="http://www.w3.org/1999/xhtml">The real design principle: one source of truth</h2><p xmlns="http://www.w3.org/1999/xhtml">The deeper decision is not “OT vs CRDT” in isolation.</p><p xmlns="http://www.w3.org/1999/xhtml">The deeper decision is this:</p><p xmlns="http://www.w3.org/1999/xhtml">Aamu.app is built around one shared workspace, not disconnected local replicas.</p><p xmlns="http://www.w3.org/1999/xhtml">That means the system needs a trusted source of truth.</p><p xmlns="http://www.w3.org/1999/xhtml">The server is where permissions are checked.<br>The server is where operations are accepted.<br>The server is where related workflow events are created.<br>The server is where search and AI context can be updated.<br>The server is where the team’s shared state becomes real.</p><p xmlns="http://www.w3.org/1999/xhtml">CRDTs are excellent when the product vision is local-first independence.</p><p xmlns="http://www.w3.org/1999/xhtml">Aamu.app is optimized for connected team workflows.</p><p xmlns="http://www.w3.org/1999/xhtml">That is why a central server and ShareDB/OT fit the product well.</p><h2 xmlns="http://www.w3.org/1999/xhtml">The tradeoff we accept</h2><p xmlns="http://www.w3.org/1999/xhtml">This architecture does have tradeoffs.</p><p xmlns="http://www.w3.org/1999/xhtml">A central server means that full offline editing is harder. It means collaboration depends on the backend being available. It means we need to operate the server reliably and keep latency low.</p><p xmlns="http://www.w3.org/1999/xhtml">Those are real costs.</p><p xmlns="http://www.w3.org/1999/xhtml">But in return, we get a simpler and more predictable model for the things that matter most in Aamu.app:</p><ul xmlns="http://www.w3.org/1999/xhtml"><li><p>permissions</p></li><li><p>consistency</p></li><li><p>auditability</p></li><li><p>workflow automation</p></li><li><p>AI integration</p></li><li><p>cross-object relationships</p></li><li><p>server-side validation</p></li><li><p>reliable team collaboration</p></li></ul><p xmlns="http://www.w3.org/1999/xhtml">For a business workspace, those properties are more important than full peer-to-peer or offline-first editing.</p><h2 xmlns="http://www.w3.org/1999/xhtml">Conclusion</h2><p xmlns="http://www.w3.org/1999/xhtml">CRDTs are an impressive technology, and they are the right choice for many collaborative and local-first applications.</p><p xmlns="http://www.w3.org/1999/xhtml">Aamu.app chooses a different path.</p><p xmlns="http://www.w3.org/1999/xhtml">Because Aamu.app is a full workspace rather than just a document editor, we care deeply about server-side correctness, permissions, audit logs, automations, search, AI context, and consistency across many types of work.</p><p xmlns="http://www.w3.org/1999/xhtml">ShareDB and Operational Transformation give us a collaboration model that fits that product vision.</p><p xmlns="http://www.w3.org/1999/xhtml">The result is a system where editing can feel real-time and responsive, while the server remains the trusted place where team data is validated, ordered, connected, and made consistent.</p><p xmlns="http://www.w3.org/1999/xhtml">In short:</p><p xmlns="http://www.w3.org/1999/xhtml">CRDTs are great for distributed editing.</p><p xmlns="http://www.w3.org/1999/xhtml">A central server with ShareDB/OT is a better fit for Aamu.app’s connected workspace.</p>
