# Newsletters in Aamu.app: from subscribers to sendingCreate newsletters, manage subscribers, design reusable templates, send test messages, publish issues, and automate the workflow through the Aamu API.Published: 2026-06-23


<p><strong>Short answer:</strong> Create newsletters, manage subscribers, design reusable templates, send test messages, publish issues, and automate the workflow through the Aamu API.</p>
<p>Newsletters in Aamu.app bring the audience, email design, individual issues, scheduling, delivery reports, and automation into the same project workspace. A team can prepare an update alongside the Docs, Tasks, Forms, and Database rows that supply its content and recipients.</p><p>The workflow starts with a Database-backed audience and ends with an explicit sending decision. Between those steps, editors can personalize the message, review the eligible recipients, send a test, and choose when the campaign should begin.</p><p><strong>Aamu implementation update, 16 October 2026:</strong> desktop and mobile previews, subscriber history, acquisition reporting and polls are implemented in the latest version. These additions appear in a workspace once that version is deployed.</p><h2>Find your way around a Newsletter</h2><p>A Newsletter has six practical areas: <strong>Issues</strong>, <strong>Subscribers</strong>, <strong>Template</strong>, <strong>Signup form</strong>, <strong>Database</strong>, and <strong>Settings</strong>. The Database holds the audience data, Subscribers provides the subscription view, and Template defines the reusable email design. Newsletter Settings contains the sending mailbox, sender name, Reply-To address, confirmation options, batch settings, and public archive settings.</p><p>Each issue opens as its own page under Issues, with three tabs:</p><ul><li><p><strong>Report:</strong> campaign progress, delivery feedback, clicks, unsubscribes, sending problems, and poll results.</p></li><li><p><strong>Content:</strong> the subject, inbox preview text, message editor, desktop/mobile and subscriber previews, HTML-size feedback, polls, and test sending.</p></li><li><p><strong>Settings:</strong> personalization fields, the campaign audience, scheduling, the pre-send review, sending controls, and publication of a public archive copy.</p></li></ul><h2>The Audience Database is the source of truth</h2><p>Creating a Newsletter also creates its Audience Database, a Subscribers table, and managed subscribe and unsubscribe automations. A signup form is optional: you can start adding recipients immediately.</p><p>Contacts can enter through the UI, CSV import, an Aamu Form, the Newsletter API, or direct Database updates. These routes converge on the same audience. The Subscribers view is a derived delivery list, so integrations do not need to maintain a second independent recipient list.</p><p>Subscription records retain the source and time of joining. A Newsletter can require <strong>double opt-in</strong>: a contact remains unconfirmed until the recipient follows the confirmation link. Only eligible active subscribers enter a production campaign; unsubscribed, unconfirmed, and blocked addresses are excluded as appropriate.</p><p>The Subscribers view supports search, status filters, and paging. Opening a subscriber shows a dialog for reviewing subscription and delivery information and editing the name or address. A permanent recipient failure can block future attempts. Where bounce re-verification is available, the recipient must confirm the address before the block is released; simply running the campaign again does not retry a known invalid address.</p><h3>Read the subscriber's history</h3><p>The subscriber dialog includes a paginated timeline of available subscription and consent events, campaigns, counted link visits and poll answers. Campaign names link back to their issues. Retained signup, confirmation and unsubscribe timestamps are labelled as current records. Aamu does not reconstruct older events that were never recorded.</p><p>Campaign entries show the latest recorded delivery outcome. Automated and repeat visits remain separate from counted clicks, and older visits without bot classification are identified. This history provides context for the relationship with a reader; it does not prove that every counted visit was human or that SMTP acceptance meant inbox delivery.</p><h2>Collect subscriptions with an optional Aamu Form</h2><p>The <strong>Signup form</strong> tab creates a public, editable Form connected to the existing Audience Database. It begins with email and name fields and remains a normal Aamu Form, with editable fields, theme, public URL, and thank-you page.</p><p>Form submissions use the same subscription automations as other audience changes. Repeated submissions update the matching subscription instead of creating duplicate delivery entries. The form does not create a separate mailing list.</p><p>Ordinary unsubscribe links open a confirmation page and update the audience when confirmed. Messages also include one-click unsubscribe headers for compatible email services. A recipient's subscription choice belongs to the relevant Newsletter; it does not automatically unsubscribe the address from every unrelated audience.</p><h3>See where subscribers came from</h3><p>Newsletter signup forms capture UTM source, medium, campaign, content and term, together with the form ID, landing page and referrer. This visitor-reported acquisition information is separate from the existing insertion source, such as an import or API addition. Later edits to subscriber details preserve the captured first signup attribution. Older contacts without captured information remain unattributed.</p><p>The subscriber dialog shows acquisition details. The Subscribers report groups source, medium, campaign and form, with deduplicated address counts, valid confirmation proof and addresses with classified production campaign clicks. It refreshes with the audience report, approximately every five minutes. Use it to compare the readers produced by different signup campaigns, while treating click-based activity as an imperfect signal.</p><h2>Reuse the design and write each issue in Content</h2><p>The content template defines the publication's repeatable structure, including the issue-content area and unsubscribe element. The outer wrapper controls the surrounding email HTML and contains exactly one <code>{{CONTENT}}</code> placeholder. It can also use <code>{{SUBJECT}}</code>. A complete HTML document with <code>html</code>, <code>head</code>, and <code>body</code> is a valid wrapper.</p><p>On an issue's <strong>Content</strong> tab, write the subject and message and add optional <strong>Preview text</strong>. This is the short summary shown beside the subject in many inboxes; it is hidden in the email body, and its display depends on the recipient's email app.</p><p>Open <strong>Preview</strong> to see the message inside the Newsletter's design, then choose <strong>Desktop</strong> or <strong>Mobile (375 px)</strong>. Enter an existing subscriber's email to preview their name and referenced Database fields. Leave it empty to check the fallback text. Use <strong>Refresh preview</strong> after changes to load the latest saved content. This preview does not send an email, alter consent or require a configured sending mailbox; rendering can still differ between email apps.</p><p>The Content tab also shows a live HTML-size estimate, including the template and poll, before personalization and tracking links. The warning starts at 85,000 bytes. The final sending review still checks each recipient's tracked HTML against the 100,000-byte limit, so the editor estimate is an early warning rather than a replacement for that check.</p><p><strong>Send test</strong> sends to the signed-in user when that address is an eligible active subscriber. It uses the real subscriber-specific unsubscribe link. Test deliveries are excluded from production campaign statistics and cannot cast poll votes.</p><h2>Ask a question and use the answer in the next campaign</h2><p>In <strong>Content → Poll</strong>, add one question and 2–10 different answer choices. Choose a separate existing text field in the Audience Database to store responses. If you need a new field, create it in the Database and use <strong>Reload fields</strong>. Identity, subscription-status and tag fields cannot be used as the answer field. Save the poll to append it to the issue.</p><p>Answer links appear in both the HTML and plain-text campaign email. Each link opens a web page where the reader confirms the answer. Opening or previewing the link alone does not vote, preventing ordinary link-scanner visits from recording answers. Aamu accepts one confirmed answer per subscriber and poll; preview and test messages cannot submit votes.</p><p>The answer is linked to the subscriber and saved to their audience row. For example, a question about product or training news can populate a <code>preferred_topic</code> text field. In the next issue's <strong>Campaign audience</strong>, add a condition that this field equals the chosen answer. This uses the existing Database field conditions.</p><p>In <strong>Report → Poll results</strong>, use <strong>Refresh results</strong> for the current answer totals and the number awaiting a Database update. A response can be recorded before its Database row is updated; interrupted updates retry automatically. If several polls share an answer field, a newer response takes precedence over an older pending response. Use separate fields when you want to retain separate answers in the audience table.</p><h2>Choose the audience and personalization in Issue Settings</h2><p>In <strong>Campaign audience</strong>, narrow the list with required tags, alternative tags, and Database field conditions. For example, a product update could target active customers with a particular subscription plan. Every field condition must match, and the final audience still has to pass the subscription and sending-block checks.</p><p>The <strong>Personalize content</strong> section lets you select a subscriber or eligible Database field and supply fallback text. Use <strong>Copy field</strong>, then paste the placeholder into the message or subject on the Content tab:</p><pre><code class="language-plaintext">Hello {{subscriber.name|friend}},</code></pre><p>Database placeholders use the selected field's ID. The field picker provides the correct placeholder. Personalization substitutes text; links, HTML attributes, and styles remain fixed. Recipient values are saved when the campaign enters the queue, so later audience edits do not silently rewrite an already queued message.</p><h2>Review, schedule, and send in growing batches</h2><p><strong>Review &amp; send</strong> checks the sender configuration, unsubscribe link, message size, and eligible audience. The review shows the sender and Reply-To address, recipient count, exclusions, batch plan, and a personalized message example. Confirming the review places the campaign in a persistent background queue.</p><p>Sending continues independently of the browser tab. Recipient-specific states record pending, successful, failed, skipped, or uncertain attempts. You can pause a campaign and continue its remaining recipients. If a connection failure leaves an attempt uncertain, Aamu pauses for review rather than automatically sending that message again.</p><p>Campaigns always use automatically growing batches. Configure the limits in the Newsletter's Settings:</p><ul><li><p><strong>Initial batch:</strong> 1–50 recipients; the default is 50.</p></li><li><p><strong>Waiting period:</strong> 24–168 hours between batches; the default is 24 hours.</p></li><li><p><strong>Growth factor:</strong> 1.1–2; the default is 2.</p></li></ul><p>Sender-domain warmup is shared across campaigns using the same domain. Growth depends on the observed sending results, and recorded delivery problems can hold or pause progress. A larger audience can therefore take several days to send; reaching the start time does not mean the whole list receives the message immediately.</p><p>To send later, use <strong>Schedule sending</strong> in Issue Settings and choose a date, time, and timezone. You can update or cancel the schedule. At dispatch, Aamu uses the latest saved content, sender settings, and eligible audience and runs the sending checks again.</p><h2>Follow delivery and engagement in Report</h2><p>The <strong>Report</strong> tab updates automatically. It separates pending and current sending work from messages accepted by SMTP, failures, uncertain outcomes, skipped recipients, reported bounces, delays, and complaints. It also shows campaign unsubscribes, recipients who clicked, total clicks, link results, recipient-domain breakdowns, and problems grouped by reason.</p><p><strong>Accepted by SMTP</strong> means the mail server accepted the submission. It does not prove that the message reached an inbox. A later delivery report can still record a failure or delay. Reported recipient failures and complaints can stop future sends, while routing or server problems are classified separately.</p><p>Click reporting distinguishes recognized automated visits and rapid repeats from counted engagement. Email scanners and privacy features can still affect the numbers, so use them as campaign signals rather than an exact record of human activity.</p><p>Subscriber profiles complement these campaign reports with a reader-level timeline. Poll response totals are available in the issue's Report tab; use <strong>Refresh results</strong> to retrieve the latest counts.</p><h2>Manage the sender in Newsletter Settings</h2><p>Before sending, connect a mailbox on a verified email domain. You can change the visible sender name and Reply-To address in Newsletter Settings. An empty Reply-To uses the sending mailbox. Queued campaigns retain the sender settings captured when they entered the queue.</p><p>Mailbox credentials are shared by Aamu features using the same managed mailbox in the workspace. The connection form checks SMTP and IMAP without sending a message. A workspace administrator can update Aamu's stored password after successful connection checks; this does not reset the password on the mail server.</p><p>Mailcow delivery feedback is matched to Aamu's tracked sends, so a newly configured sender does not require a separate per-address feedback switch. Feedback processing is monitored, and repeated delivery or complaint problems can pause sending and alert administration.</p><h2>Publish a public archive separately from sending</h2><p>Enable the public archive in Newsletter Settings, then preview and publish an issue's <strong>Public archive copy</strong> from its Settings tab. Sending an email and publishing a web page are separate actions.</p><p>The public copy uses fallback text instead of recipient-specific personalization. Review it for any personal information written directly into the message. Publishing creates a snapshot: later editing does not change the public page until you publish an updated copy. You can also unpublish an issue.</p><p>The archive provides shareable issue pages. A custom hostname requires domain ownership verification and the corresponding DNS and hosting setup. Integrations can use the Newsletter API to build their own publication frontend as well.</p><h2>Automate the same workflow through the API</h2><p>The project-scoped Newsletter API can manage Newsletters, draft issues, subscribers, audience selection, previews, polls, subscriber history, reviews, scheduling, reporting, and archive publication. Requests use a Team API key with the appropriate Newsletters scope and the project header:</p><pre><code class="language-plaintext">x-api-key: YOUR_API_KEY
x-project-id: YOUR_PROJECT_ID
Content-Type: application/json</code></pre><p>Create a draft with a subject, HTML, and optional inbox preview text:</p><pre><code class="language-plaintext">POST /api/v1/newsletters/{newsletterId}/issues
{
  "subject": "Product update",
  "preview_text": "What changed and what is coming next",
  "html": "&lt;p&gt;Hello {{subscriber.name|friend}},&lt;/p&gt;&lt;p&gt;Here is this month's update.&lt;/p&gt;"
}</code></pre><h3>Preview, inspect reader history, and configure a poll</h3><p>The read-only preview can use a subscriber's values, or fallback text when <code>subscriber_email</code> is omitted. Subscriber history returns a page of events and an opaque <code>history.nextCursor</code>; pass it as <code>cursor</code> for older entries.</p><pre><code class="language-plaintext">GET /api/v1/newsletters/{newsletterId}/issues/{issueId}/preview?subscriber_email=reader%40example.com
GET /api/v1/newsletters/{newsletterId}/subscribers/{subscriberId}/history
GET /api/v1/newsletters/{newsletterId}/subscribers/{subscriberId}/history?cursor=NEXT_CURSOR</code></pre><p>Save a poll on a draft issue using the audience text field's <code>gtype</code>:</p><pre><code class="language-plaintext">PUT /api/v1/newsletters/{newsletterId}/issues/{issueId}/poll
{
  "question": "What would you like to read about next?",
  "options": ["Product news", "Training"],
  "field": "preferred_topic"
}

GET /api/v1/newsletters/{newsletterId}/issues/{issueId}/poll/results
DELETE /api/v1/newsletters/{newsletterId}/issues/{issueId}/poll</code></pre><p>Preview, history and results require Newsletters read permission. Saving or removing a draft poll requires write permission and the normal API actor checks. Issue responses include <code>poll</code>, subscriber responses include <code>acquisition</code>, and the audience report includes the acquisition breakdown. Poll configuration is frozen with the queued campaign.</p><h3>Review and send explicitly</h3><p>Send a test, then request the production review. Pass its returned <code>review.token</code> when confirming the send:</p><pre><code class="language-plaintext">POST /api/v1/newsletters/{newsletterId}/issues/{issueId}/send-test

POST /api/v1/newsletters/{newsletterId}/issues/{issueId}/review

POST /api/v1/newsletters/{newsletterId}/issues/{issueId}/send
{
  "review_token": "TOKEN_FROM_REVIEW"
}</code></pre><p>The send endpoint returns <code>202</code> with <code>queued: true</code>; it does not wait for every recipient to be sent. A changed subject, content, sender, audience, poll configuration, or batch configuration invalidates the supplied review token and requires another review.</p><p>Scheduling and cancelling use separate operations:</p><pre><code class="language-plaintext">POST /api/v1/newsletters/{newsletterId}/issues/{issueId}/schedule
POST /api/v1/newsletters/{newsletterId}/issues/{issueId}/cancel-schedule</code></pre><p>The schedule request supplies <code>send_at</code>, <code>timezone</code>, and the review token. The optional signup form is created idempotently with <code>POST /api/v1/newsletters/{newsletterId}/signup-form</code>. Direct Audience Database updates use the same managed subscription automations. Subscriber API responses do not expose private unsubscribe tokens.</p><p>For AI and other automations, keep creating or editing a draft separate from permission to send it. A review can prepare the decision; delivery remains an explicit action.
