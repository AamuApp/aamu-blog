# AI commands in Aamu.app: turning comments into workspace actionsHow Aamu.app AI routes natural-language requests to workspace operations across tasks, Docs, Forms, databases, automations, Helpdesk, Email, meetings, and files.Published: 2026-06-15


<p><strong>Short answer:</strong> How Aamu.app AI routes natural-language requests to workspace operations across tasks, Docs, Forms, databases, automations, Helpdesk, Email, meetings, and files.</p>
<p>You can ask Aamu AI to act on the task, meeting, ticket, email, Doc or database row you are viewing.</p><p>For example, <code>@ai Move this meeting to tomorrow at 13:00</code> uses the current meeting as context for a scheduling change.</p><p>Commands can start in comments, chat or the AI panel.</p><h2>From answer bot to action router</h2><p>A plain AI answer is text. An AI command is text plus intent, context, validation, and a product action.</p><p>When a user writes a request, Aamu first decides what kind of request it is. Is the user asking for a general answer? A task draft? A reply draft? A meeting update? A database row change? That intent routing step matters because different requests need different safeguards.</p><p>The routing has two levels. First, an intent router recognizes common workspace actions such as creating a task, updating a Doc, changing a meeting, or editing the current database row. For the broader operation set, Aamu then selects a specific operation from the same OpenAPI-described surface used by the public Aamu API and builds arguments from that operation's schema.</p><p>This does not mean the internal AI needs an API key or makes an external HTTP request back into Aamu. The operation is executed inside Aamu with the signed-in user's session and project access, reusing the existing product handlers and server-side functions.</p><h2>Ask Aamu for product help</h2><p>Not every request should become a workspace action. In the Launch AI dialog, prefix a question with <code>aamu:</code> when you want to ask how Aamu.app works:</p><pre><code class="language-plaintext">aamu: How do I share a Doc with a public link?</code></pre><p>This routes the question to Aamu's dedicated product-help assistant before the normal workspace action router. It searches Aamu's public documentation, returns supporting source links, and does not use the current team's Team Brain or modify workspace data.</p><p><a target="_blank" rel="noopener noreferrer nofollow" href="/blog/posts/ask-aamu-for-product-help-with-ai/">Read more about Ask Aamu and the public Support API.</a></p><h2>Where commands can start</h2><p>The command does not have to start in one dedicated AI page. It can come from several places:</p><ul><li><p><strong>The AI panel</strong>, where the user asks Aamu to work with the current page. Use <code>aamu:</code> when the request is product help rather than a workspace action.</p></li><li><p><strong>Comments with @ai</strong>, where a normal workspace discussion can include an instruction to AI.</p></li><li><p><strong>Chat messages</strong>, where a team conversation can ask AI to create follow-up work or use the current chat as context.</p></li><li><p><strong>Feature-specific AI buttons</strong>, such as Helpdesk triage and support reply drafting.</p></li></ul><h2>What Aamu can do today</h2><p>The current command set focuses on actions that fit naturally inside a team workspace.</p><ul><li><p><strong>Create task drafts</strong> from the current context, such as a support conversation, email, document, chat, or database row.</p></li><li><p><strong>Update existing tasks</strong> when the task can be resolved from the current page or instruction.</p></li><li><p><strong>Create and update Docs</strong> for internal knowledge and follow-up writing.</p></li><li><p><strong>Draft or rewrite replies</strong> for Helpdesk tickets and email threads while keeping sending as a separate step.</p></li><li><p><strong>Create email drafts</strong> for outbound communication.</p></li><li><p><strong>Create meetings</strong> and update existing meetings.</p></li><li><p><strong>Create and update Forms</strong>, define questions, publish the form, find existing forms, and submit database-backed responses.</p></li><li><p><strong>Create and extend databases</strong>, add tables and columns, and create, update, query, or link database rows.</p></li><li><p><strong>Manage database automations</strong>, including listing, creating, updating, and deleting automation definitions.</p></li><li><p><strong>Use database GraphQL</strong> when an operation needs the generated schema for structured row queries or mutations.</p></li><li><p><strong>Work with files, project users, contacts, Helpdesk, and Email operations</strong> that are available through Aamu's broader operation surface.</p></li><li><p><strong>Search Docs</strong> when the user is asking for existing written knowledge.</p></li></ul><p>The practical boundary is now close to the public Aamu API's operation set. The difference is authentication and context: an external integration uses an API key and explicit scopes, while the internal AI uses the signed-in user's workspace permissions and the page or conversation already open in Aamu.</p><h2>How Aamu chooses an operation</h2><p>A broad tool list is useful only if the assistant can select the right tool and fill it safely. Aamu uses a staged process:</p><ol><li><p>The intent router separates a general answer from a concrete product action.</p></li><li><p>Established context-aware actions, such as task, Doc, meeting, reply, and current-row commands, keep their specialized handling.</p></li><li><p>Other product actions are matched to one OpenAPI operation, such as <code>createForm</code>, <code>updateForm</code>, <code>submitForm</code>, <code>addDatabaseColumns</code>, <code>createDatabaseAutomation</code>, or <code>databaseGraphQL</code>.</p></li><li><p>The selected operation's schema guides the path parameters, query parameters, and request body.</p></li><li><p>The normal server-side validation and product handler execute the action with the user's accessible projects.</p></li></ol><p>Using the operation schema reduces guesswork, but it does not remove product safeguards. If an id, project, database, required field, or permission is missing, the underlying handler rejects the operation instead of allowing the model to bypass validation.</p><h2>Example: creating a Form from the AI panel</h2><p>A user can ask:</p><blockquote><p>Create a Form called Contact Form that asks for a name and email address.</p></blockquote><p>Aamu maps that request to the Forms API <code>createForm</code> operation. The operation schema tells the AI that the request needs a name and a list of typed fields. Aamu creates the Form in the selected project and opens it in the Form editor, where the user can review it, add more questions, or publish it.</p><p>The same operation is available to external integrations through <code>POST /api/v1/forms/</code>. Internal AI uses the signed-in user's access instead of an API key, but both paths share the same validation and Form creation behavior.</p><h2>Example: rescheduling a meeting from a comment</h2><p>A meeting comment might say:</p><blockquote><p>@ai Move this meeting to tomorrow at 13:00</p></blockquote><p>Aamu needs to identify the meeting and interpret the requested time before applying the change.</p><p>For this to work well, Aamu has to pass the right context into the command:</p><ul><li><p>the source type is a meeting, not just a generic page;</p></li><li><p>the existing meeting id, title, start time, end time, and invitees are available;</p></li><li><p>the user's timezone and browser offset are included, so "tomorrow at 13:00" is interpreted as the user's local time;</p></li><li><p>the command result updates the meeting instead of only writing another comment.</p></li></ul><h2>Why timezone details matter</h2><p>Time commands are deceptively hard. "Tomorrow at 13:00" is clear to a human because the human silently applies local time. A server does not know that unless the client or user profile tells it.</p><p>Aamu sends both the user's timezone name and the browser timezone offset with AI commands where time may be interpreted. The timezone name is useful as a stable user preference. The browser offset is useful because it reflects the user's current environment, including daylight saving time.</p><p>This matters for meeting updates, task dates, reminders, and any future command that turns natural language into a timestamp. Without it, a command can look correct in the AI reply while storing the wrong time.</p><h2>Example: turning a conversation into a task</h2><p>A common team pattern is that a conversation creates follow-up work. Someone explains a customer issue in a Helpdesk ticket, email thread, chat, or meeting note, and the next step is obvious: make a task for the team.</p><blockquote><p>@ai Create a task to check why this customer cannot import contacts. Assign it to support and include the relevant details.</p></blockquote><p>The useful task draft should not only contain the sentence the user typed. It should use the current context as source material: the ticket, email thread, chat, or row the user was looking at. It should produce a clear title, useful body, and link back to the original item when possible.</p><h2>Example: editing CRM data from the row itself</h2><p>The new <a target="_blank" rel="noopener noreferrer nofollow" href="/blog/posts/how-to-use-aamuapp-as-a-small-team-crm/">small-team CRM template</a> is a good example of why AI commands become more useful when the data is structured.</p><p>A user might open a deal row and say:</p><blockquote><p>@ai Move this deal to Proposal, set probability to 60%, and link the primary contact to Anna from Northwind.</p></blockquote><p>That is not just a writing task. It is a database operation. Aamu needs to know the current row, the table columns, the available reference targets, and which fields are safe to change. The command router can then choose between updating the current row, creating a new row, or linking the current row to another row.</p><h2>Human review still matters</h2><p>Aamu's AI support features already follow a human-in-the-loop model. A generated Helpdesk or email reply is a draft until someone sends it. That principle still applies when commands become more action-oriented.</p><p>Not every command should be automatic, and not every action has the same risk. Creating a task draft is low risk. Sending a customer reply is higher risk. Updating a meeting time affects other people. Changing CRM data affects reporting and follow-up. A useful AI command system needs product boundaries, not only model confidence.</p><p>Aamu therefore requires explicit intent or confirmation for higher-risk operations such as sending messages, deleting an automation, or running a GraphQL mutation. Read operations and ordinary reversible workspace edits can remain more direct.</p><h2>How this fits with Team Brain</h2><p>Some requests need an answer or an existing Doc rather than a workspace change. <a target="_blank" rel="noopener noreferrer nofollow" href="/blog/posts/how-aamuapp-uses-team-brain-to-answer-from-your-company-knowledge/">Team Brain</a> supplies maintained knowledge for supported AI workflows. See also <a target="_blank" rel="noopener noreferrer nofollow" href="/blog/posts/ai-support-in-aamuapp/">Aamu’s AI support workflow</a>.</p><p>A command can use the current page as context and also retrieve related Docs or Team Brain material. That makes the result less generic. A support draft can use the latest policy. A task can include the relevant troubleshooting detail. A Doc update can reflect the source conversation instead of starting from memory.</p><h2>Why comments are a natural command surface</h2><p>Comments are already where teams say what should happen next. People write "can someone follow up?", "move this to next week", "turn this into a doc", or "connect this to the customer record" all day long.</p><p>Adding <code>@ai</code> to that flow makes the instruction explicit without moving the user into a separate automation builder. It also keeps the action visible in the same place as the discussion. The team can see that AI was asked to help, and the resulting task, meeting, draft, or row remains connected to the original work.</p><p>This is not a replacement for buttons, forms, or careful workflow design. It is a faster path for the cases where the user can describe the intended action more naturally than they can click through several screens.</p><h2>Related articles</h2><ul><li><a href="/blog/posts/building-with-the-aamu-api-from-tasks-to-docs-and-graphql/">Building with the Aamu API: From Tasks to Docs and GraphQL</a></li><li><a href="/blog/posts/database-automations-with-aamuapp/">Database automations with Aamu.app</a></li><li><a href="/blog/posts/from-form-submission-to-follow-up-workflows-with-aamuapp/">From form submission to follow-up: workflows with Aamu.app</a></li><li><a href="/blog/posts/aamuapp-databases-practical-feature-guide/">Aamu.app Databases: a practical feature guide</a></li><li><a href="/blog/posts/aamuapp-docs-feature-overview/">Aamu.app Docs - feature overview</a></li></ul>
